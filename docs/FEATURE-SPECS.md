# Five-feature implementation specifications

All behaviors are planned. [PRD](../PRD.md) owns requirements, [controls](controls.yaml) owns numeric defaults, and [contracts](STATE-DATA-API.md) owns state semantics.

## F1 — approved recipes and camera enrollment (R01–R03)

Owner creates a draft recipe with a short name, opaque kit SKU, four-class catalog references, expected counts, permitted broad variants, optional planar dimension intervals, and explicit exclusions. Part-class choices begin as washer, nut, bolt and flat bracket; actual specimens must determine which distinctions are reliably observable. Printable stand-ins are separate fixture classes and may not qualify hardware recipes.

Schema: `recipe_id`, monotonically increasing `revision`, `status`, `constraints[]`, `reference_asset_ids[]`, `calibration_profile_id`, `qualification_run_id`, `approved_by`, `approved_at`, `content_hash`. Each constraint has `constraint_id`, `part_class_id`, integer `expected_count` (0–20), optional `min_mm/max_mm`, `permitted_variant_ids`, `required_visibility`, and `unsupported_properties[]`. Bound total items to 30 for the first release; these are usability/compute limits, not an assertion that 30 can be measured accurately.

Calibration: generate a printable fiducial mat with a measured scale. Operator must physically check the printed scale because fit-to-page changes dimensions. Enroll image size, marker positions, camera lens profile, ROI, illumination envelope and a reference ruler measurement. Owner approves only after a qualification report is linked; synthetic evidence may activate only a synthetic recipe in non-beta environments. Physical recipe activation requires real-part evidence.

Draft -> QUALIFICATION_PENDING -> APPROVED -> RETIRED. Editing an approved recipe creates a new revision. Changing active revision invalidates current sessions referencing the previous active revision. No silent mutation. Historical reports preserve old revisions even after retirement, subject to documented privacy deletion of media.

Implementation steps: typed validation; repository layer; private reference-asset handling; calibration UI; immutable approval event; active-revision transactional write; requalification preview. Workbench exposes which tests changed or failed before activation. Error paths: conflicting approval returns 409; missing asset or qualification returns 422; unsupported calibration returns review-required. Owner can retire, not erase history through ordinary CRUD.

Acceptance: invalid ranges/counts rejected; operators cannot approve; copied reference IDs from another deployment rejected; old results invalidated on revision change; failed calibration never activates a physical recipe. Tests T01–T03. Evidence E01, E06.

## F2 — measurement and scene tracking (R04–R06)

Browser obtains camera permission only when the operator starts capture. Crop the source camera to the indicated calibrated capture rectangle, including all enrolled mat markers; display exactly that transmitted rectangle before upload. Its dimensions and marker coordinates must match the enrolled profile. Distinguish it from the smaller rectified work ROI retained as selected evidence: markers and other pixels inside the capture rectangle are still transmitted transiently. Backend distrusts client content type, dimensions and metadata. Decode in a resource-limited process, normalize orientation, detect calibrated mat, rectify supported plane, score quality, segment candidates and compute counts/shape/planar measurements. Track scene changes and report unknown regions. Never treat a low detector score as a calibrated probability. Actual browser cropping/privacy preview remains a rendered workflow acceptance requirement.

Output: observation identity and provenance; quality failures; object candidates with boxes/masks and measurable features; constraint-level SATISFIED/VIOLATED/UNOBSERVABLE; scene generation; timing; build identity. No model-generated count or dimension is accepted as a measurement.

Require sufficient pixel resolution and an independently measured error envelope to distinguish variants. A bolt whose enrolled planar projection cannot be resolved, or two near-identical nuts outside calibrated discrimination, stays UNOBSERVABLE. One overhead image cannot measure physical 3D flatness. Optional flat_reference_aspect_ratio bounds describe only the enrolled visible projection; absent bounds never imply pose measurement. Extra/unrecognized objects prevent passing until removed or explicitly permitted by the recipe. Motion clears the stability window. Small accepted appearance changes still require all constraints to be re-evaluated at every observation.

Implementation steps: OpenCV runtime proof; fixtures and geometry unit tests; quality filters; part-feature prototypes; interval/error model; tracking; worker limits; measured on-AWS path. See [pipeline](OPENCV-PIPELINE.md). Tests T04–T07, T24–T25. Evidence E02, E03, E10.

## F3 — bounded active inspection (R07–R08)

The planner receives only structured current findings, safe action candidates and optional prior approved outcome statistics. Its task is to choose the next observation that could resolve an outstanding constraint. Actions: RECAPTURE, SEPARATE_REGION, PLACE_FLAT, REVIEW. The UI uses server-owned action templates, decision summaries and overlays; no arbitrary generated physical instruction. On candidate action selection, create an action ID bound to inspection version, scene generation and observation. Reinspection after operator completion must belong to that same inspection and satisfy its conditions.

Initial deterministic policy: uncertainty type filters valid actions; rank supported candidates by approved development-set resolution rate per operator second; if evidence is sparse, use documented static ordering and mark the mode. An optional Bedrock adapter may propose the same enum under a fixed JSON schema. It has no credential, HTTP, shell, recipe-update, storage-path or pass-state tool. A schema validator and the same action allowlist check its output.

Provider attempts use durable decision reservations and the model-call/concurrency limits in [controls](controls.yaml). Duplicate or uncertain requests cannot trigger an uncharged provider retry; see [agent design](AGENT-DESIGN.md).

At most two corrective requests per inspection, charged transactionally when issued and preserved across retries and reloads. Terminal REVIEW is an escalation, not a third correction. Tool/planner timeout leads to REVIEW_REQUIRED; transport retries do not reset the budget. An invalid action does not become an automatically retried new model request. Human correction alone never passes a kit: F2 and F4 must verify fresh evidence. Acknowledgment without changed evidence produces unresolved state.

Tests T08–T10 compare actual observation-to-action traces, unsupported action rejection and budget persistence. E04 contains the exact policy mode/model ID, approved alternatives, selected action, visual evidence ID, tool outcome, duration and escalation reason. Store concise decision summaries, not hidden chain-of-thought.

## F4 — verifier and evidence (R09–R11)

A pure deterministic verifier evaluates approved bindings, quality, complete observable constraints, stability, current session/epoch and evidence freshness. Only it proposes a pass. A conditional transaction commits the new status and event; stale writes fail. Client status is always derived from server-effective state and a local conservative deadline. It cannot set `passed=true`.

Prioritize invalidation ahead of planner completion. Scene change, changed recipe/calibration/policy, station takeover, expired observation, network failure or process restart removes current pass eligibility. A historical snapshot remains labeled historical. A human override creates a separate disposition and does not alter the machine state. Closing an inspection produces a historical record with last observation time; it never creates a durable shipping authorization.

Persist selected evidence before publishing a pass record. If storage is unavailable or an evidence commit fails, display REVIEW/EVIDENCE_UNAVAILABLE. Record metadata and bounded selected frames; do not retain continuous video by default. Export a manifest with hashes, versions, ordered events, omitted/deleted-media notices and outcome. Hashes show consistency with the manifest, not authentic capture.

Tests T11–T16 exercise the full state machine, races, retries, restart, replay, human disposition and evidence reconciliation. E05/E06 are traceable runtime records from the same code/config revision as the candidate release.

## F5 — outcome review and replay (R12–R13)

Reviewer labels before/action/after tuples as resolved/unresolved/incorrect finding with ground-truth counts, review method and duration. Label corrections create revisions. Operator agreement alone is not independent truth. Keep `data_origin` (synthetic/printable/physical), `reviewer_independent`, allowed purpose, consent reference and deletion deadline on every example.

Separate DEVELOPMENT, VALIDATION and FROZEN_TEST by physical kit/session/operator grouping. A test-access log records who inspected the holdout. Once test examples influence a change they become development data; create a new untouched test set and explicitly retire the old benchmark. No live threshold learning. Candidate policy/recipe changes replay golden, regression and safety cases, then require owner approval to activate. Promotion records data manifest, results, versions and approver; rollback follows the same binding invalidation.

The workbench supports label, replay, compare, approve and export as one coherent review flow. The independent validation register is separate from training data and records the actual external observer, context, failures and limitations. No customer-sharing pool or vector database.

Tests T17–T19 prove split isolation, label lineage, promotion blocking and rollback. E07/E08 prove the mechanism; no learning moat claim until accumulated data demonstrably improves untouched outcomes against a strong rule baseline.

## Complete lifecycle coverage

[Workflow acceptance](WORKFLOW-COVERAGE.md) maps all persona steps to T01–T58. F1 additionally requires scoped reference upload/retention and explicit calibration approval/retirement (T35/T36/T41); F2 requires tolerance/coordinate and freshness checks (T44/T46). F3 requires latest-observation proposal revalidation and deployment inference allowance (T45/T49). F4 requires station allocation/release, originating grant/runtime/control authority, app-proxied evidence delivery and terminal close/recovery (T37–T40/T46–T48/T51–T54). F5 requires reviewed independence, purpose/revision fences and bounded leased/cancellable jobs (T41–T43/T52). Cross-cutting onboarding/recovery/ownership/exit/judge/accessibility uses T31–T34/T50/T55–T58.

These operations complete the existing five-feature contracts; they add no portal, role, public onboarding or automatic shipping. Missing reference/evaluation permissions or configured job/worker bounds deny the affected workflow. A data-authority epoch synchronously fences changed permissions/ground truth and stale jobs; it does not certify the physical origin of browser pixels.

## F1 local implementation boundary

Camera enrollment now has a fixed printable desktop-v1 mat, bounded stored-reference diagnostics, immutable draft revisions and qualification jobs/reports, separate explicit owner approval/retirement and rendered owner/reviewer support. Two-to-eight expected supported/rejected cases are developer test intent; successful diagnostics do not establish physical truth. Synthetic practice approval is development-only. Required physical assurance is separately bound and reviewer-dependent; genuine assurance creation/import and independently qualified prints/lenses/specimens are still missing. Full F1 acceptance remains open; current results and failure limits are recorded in BUILD-STATUS and TEST-PLAN.

## F5 current operational-label boundary

Reviewer-only operational labels now bind permitted completed observations or acknowledged ordered correction tuples, reconstructed capture provenance, recipe/software/geometry identity and opaque origin groups. Immutable content-hashed revisions preserve corrections and conflicts; a data-authority change fences in-flight work. Owner reads do not grant reviewer writes; declared ground truth/duration/independence remain unverified. Rendered creation/correction/retry and local source/authorization/lineage checks exist. Labels alone supply no optional reuse permission or reviewed independence. A separate owner-only selected-source improvement permission workflow now exists locally; it leaves operational flags unchanged, requires current separate notice/expiry/scope and supports withdrawal. Durable 1–1000-example dataset preparation, persistent split classification, audited metadata delivery and explicit retirement/declassification now have a local implementation under verification. Replay/evaluation/promotion and learning benefit remain unfinished/unaccepted. Complete F5 acceptance remains open; see BUILD-STATUS and TEST-PLAN.

## F1 measured recipe qualification boundary

A local stored-case job/report path now measures complete/incorrect/challenge comparisons with the existing isolated OpenCV worker and shared capacity. It binds current draft, calibration source proofs, artifact/environment/data authority, case/reference purposes and operational notice. Intact hashed reports are mandatory for approval and active reads, with no report-less fallback. Passing diagnostics can support separate owner review in non-beta synthetic/printable contexts; owner-declared physical success is explicitly withheld pending independent physical assurance. Physical assurance/import, real specimens, actual target proof and complete F1 acceptance remain unfinished. See STATE-DATA-API for current-result selection and BUILD-STATUS for actual current-source verification.


## F4 local inspection-export boundary

Selected-original prerequisite: an owner separately attests the current original-retention notice on a new operational purpose, an administrator explicitly configures its use, and the originating operator selects a single next original. Default off; three nonrefundable permit attempts per inspection; exact transmitted JPEG/PNG at most 2 MiB; expiry no later than purpose expiry or admission plus seven days. Original and crop object intents/verified receipts link atomically before publication. Bounded authenticated discovery/review, current original/crop/calibration/source checks, separate owner metadata/body privilege, explicit export lineage/omissions and selected frame-version cleanup are implemented locally. Review labels preserve both sources and dataset preparation requires independent source plus review-data reuse scope for all included assets. Current verification belongs to BUILD-STATUS. This does not complete full vision replay, qualification/promotion, privacy fulfillment or actual-target/human acceptance.

An explicit operator/reviewer path now prepares a bounded immutable historical manifest, including source versions/digests, recorded software/recipe/camera/policy bindings, terminal observations, matching ordered completion events, intact human decision/correction history and omitted/deleted-media notices. Origin is recorded only for selected assets; physical truth, capture authentication, current approval and optional reuse are never inferred. Private source digests are not independently reproducible from sanitized fields alone.

Durable kind-dispatched jobs, runtime-bound leases, nonrefundable scan reservations, current permissions/data/source/config checks, cancellation and session-bound one-use ticket delivery now have local implementations. In-memory uncompressed ZIPs contain the manifest and up to three newly authorized pinned media objects; no additional S3 archive copy is retained. The workbench bounds/verifies bytes and clears local capabilities/copies on expiry/interruption/forget. Ready does not prove receipt. Manual advances do not satisfy the separate maintenance-worker driver requirement. Full W14, actual AWS/retention/recovery, human understanding and complete privacy fulfillment remain unaccepted.

F5 labelled datasets require a separate explicit optional right to associated outcome counts/method/duration metadata, not image permission alone. Existing image-only grants remain unchanged and cannot prepare labelled examples. Split assignments are derived from provenance and persist across manifests; a current owner may declassify to development with an audited DATA change, never upgrade exposed development data to frozen status. Frozen data remain unqualified for independent benchmark claims until actual protocol/rights/truth and cross-surface exposure evidence exist.

F5 installed candidate prerequisite: reason_priority_v1 limits proposals to a permutation of three existing eligible corrective actions with unchanged REVIEW/verifier/budgets. Local reviewer create/revise and owner/reviewer metadata catalog/readback provide immutable lineage and explicit uncertain recovery, never policy-active mutation. Decision replay of historical measured tuples is distinct from new vision measurement of qualified inputs; cropped derived evidence is not automatically a full-frame replay source. Diagnostic replay does not close complete four-baseline/golden/safety evaluation, independent qualification, promotion/rollback or live integration.

F5 historical diagnostic implementation: decision_replay_v1 now has strict exact-input requests, signed original-reviewer maintenance dispatch, one-example nonrefundable leases, immutable chain/report, separate current owner summaries and reviewer-only audited example pages, explicit cancellation/retirement and a Historical comparisons workbench. Every completed example remains in exactly one classification per policy; mismatched proposed actions have unknown counterfactual outcomes. Declared review duration is not operator effort. Source/label/permission/DATA/runtime changes and expiry hold current use; neither a partial result nor a frozen split establishes independent qualification. Reviewer and owner actions retain existing role/MFA/current-source checks and immutable retries. Opt-in original-frame reprocessing now has locally verified service/worker/workbench paths with exact geometry, source/recipe bindings and declared-count unknowns. Complete four-baseline/golden/safety evaluation, equal-budget physical comparisons, independent qualification, activation/rollback and actual user/target acceptance remain required. Latest source-bound verification and failures are owned by BUILD-STATUS, not inferred from source presence.
